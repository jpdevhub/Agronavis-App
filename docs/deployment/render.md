# Deploying the API to Render

The repository ships a [`render.yaml`](../../render.yaml) blueprint. Render reads
it and provisions the service; you supply four secrets.

## 1. Create the service

1. Push this repository to GitHub.
2. In Render, **New ▸ Blueprint**, choose the repo, and let it read `render.yaml`.
3. Render prompts for the values marked `sync: false`:

   | Variable | Where it comes from |
   |---|---|
   | `SUPABASE_URL` | Supabase ▸ Project Settings ▸ Data API |
   | `SUPABASE_SERVICE_ROLE_KEY` | Supabase ▸ Project Settings ▸ API Keys ▸ secret |
   | `OPENWEATHER_API_KEY` | openweathermap.org ▸ API keys |
   | `AGMARKNET_API_KEY` | data.gov.in ▸ profile |

   `TOTP_ENCRYPTION_KEY` is generated by Render and kept for the life of the
   service. Everything else has a value in the blueprint.

4. Deploy. The build runs:

   ```
   npm ci --workspace=@agronavis/backend --include-workspace-root
   npm run build --workspace=@agronavis/backend
   ```

   That installs only the API's dependency tree — roughly 285 MB and under a
   minute. Installing the whole workspace would pull in Expo's native packages,
   about 700 MB the server never loads.

Render sets `PORT`; the server reads it and binds all interfaces. `/health` is
the health check and is exempt from rate limiting.

## 2. Point the app at it

Once the service is live, put its URL in the root `.env`:

```
EXPO_PUBLIC_API_URL=https://agronavis-api.onrender.com/api/v1
```

and in the GitHub repository secrets used by the EAS workflow
(`EXPO_PUBLIC_API_URL`), then rebuild the app. The URL is compiled into the
bundle, so a running app cannot be re-pointed without a new build.

Native apps send no `Origin` header, so `ALLOWED_ORIGINS` does not affect them.
Add an origin only when a browser needs to call the API — the Expo web build, or
the enterprise console.

## 3. What the free plan costs you

A free Render web service **sleeps after 15 minutes without traffic** and takes
roughly 50 seconds to wake. Two consequences, both real:

- **The first request after idle is slow.** The app's axios timeout is 30 s by
  default, so a cold start can surface as a timeout to the user. Raise
  `EXPO_PUBLIC_API_TIMEOUT` to `60000` if you stay on the free plan.
- **The cron jobs only run while the service is awake.** `node-cron` lives in
  the process; a sleeping process fires nothing. Advisories will be generated in
  bursts when someone opens the app rather than every 30 minutes.

Three honest options:

| Option | Effect |
|---|---|
| Accept it | Advisories generate on first use each session. Fine for a pilot or a demo. |
| Ping `/health` every 10 minutes from a free external cron (for example cron-job.org) | Keeps the instance awake and the jobs on schedule. It also consumes the free plan's monthly instance hours faster. |
| Move to Render's paid Starter plan | No sleep, jobs run on schedule. |

Set `ENABLE_JOBS=false` if you would rather the pollers never run than run
irregularly.

## 4. Verifying a deploy

```bash
curl https://<your-service>.onrender.com/health
```

```json
{ "status": "healthy", "service": "agronavis-api", "environment": "production" }
```

If the service exits at boot, the log line names the cause. The most common is:

```
Supabase rejected the connection: Invalid API key
```

which means `SUPABASE_SERVICE_ROLE_KEY` belongs to a different project than
`SUPABASE_URL`. The two must come from the same Supabase project.

## 5. Database migrations

Render does not run migrations. Apply them from a machine with the Supabase CLI
logged in:

```bash
npx supabase link --project-ref <your-project-ref>
npm run db:push
```

Migrations in `supabase/migrations` are written to be idempotent, so re-running
is safe.
